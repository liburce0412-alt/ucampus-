## 四、失败模式（全部有现场证据，可直接复用为检查项）

### 1. While 长对话采不到音频（已用对照实验确认）

先启动 UID 采音、再点播放，40 秒后 `rms = 0.0`、`peak = 0`。
Pre 的短句走同一条采集路径却能被采到。结论：**While 的长对话走另一条音频路径，
UID 采集拿不到。** 因此 While 只能靠题目语义判断，命中率约 50%，
这是听力分数落在 22–74 的直接原因。

复现要点：两个 `target_audio_capture.py` 进程不得并发；采音要先于点击播放启动；
`ready.json` 里的 `uid` / `mode` 必须与本次一致。

### 2. 采音有约 60 秒上限

单次 `target_audio_capture.py` 超过约 60 秒报 `Capture exceeded its sample limit`，
连续调用也会受影响。因此 `capture` 步骤的 `seconds` 不能直接按课文长度填，
需要复核读数策略。

### 3. 点已展开的句子卡片正文 = 立刻覆盖已有分数

会立即开一段新录音，把已经拿到的分数覆盖成 0。本轮犯了 3 次，
重录后分数普遍下降约 10 分。**这是唯一一条会造成不可逆数据损失的操作。**

规避：卡片只点左侧（见 [GESTURES.md](GESTURES.md)）；点击前后各用一次
`ob` 比对分数节点，不要连点。

### 4. 滑动被识别成点击

滑动列表时手势偶尔被判成点击，可能顺带触发选项或录音。
滑动之后必须用 `ob` 复核分数与选中状态，不能假定滑动无副作用。

### 5. 短句评分波动

「Mornings are awful.」这类短句评分方差很大，同样内容重复录一次通常能涨分。
这不是缺陷，是打分器特性；但重录的代价要算进耗时。

## 五、执行器（`workflow_session.py`）在本轮的真实表现

本轮**大部分时间没有走整阶段执行器**，而是用 `bc.py ob` / `ct` 逐条驱动。
执行器只在 11-06 的短词直送路径上真机跑通过一次，实测：

| 指标 | 值 |
|---|---:|
| 计划步骤 | 1 |
| `bridge_reads` | 70 |
| `clicks` | 0 |
| `elapsed_seconds` | 18.063 |
| 模型往返 | 1 |
| 模型可见输出 | 898 字节 |

同一时期逐步模式的读数密度是 **1.01 次设备读 / 次模型往返**，
执行器是 **70 次设备读 / 次模型往返**。两者的差别不在设备动作数量，
而在设备动作被暴露给模型的次数。完整的往返与 token 对比见
[TOKEN-NOTES.md](TOKEN-NOTES.md)。

离线计划校验（不连设备）已纳入本次记录：

```powershell
python -X utf8 workflow_session.py examples/plan-listen-while.json --validate
# {"valid":true,"steps":1,"device_contacted":false}
```
