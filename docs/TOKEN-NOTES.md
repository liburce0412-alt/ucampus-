# 会话用量与往返次数的实测口径

本文回答一个具体问题：**同一套工具，为什么整周跑起来又慢又耗 token？**
回答只引用本地会话日志里的用量元数据和执行器自己的计数，不估算金额，不把字节数换算成 token。

数据采集于 2026-11-10，覆盖本机一次真实的整周训练（2026-11-01 → 2026-11-10）。
原始会话日志属于个人数据，不随仓库分发；复现命令见文末。

执行侧的耗时回归已经写在 [测量口径与限制](BENCHMARKS.md#2026-11-10-实际耗时回归) 里，
那一节末尾明确留了一句「修复后的端到端耗时与 token 降幅也尚未建立」。本文补的是那半句：
把模型往返次数和 token 元数据单独量出来，并说明两者的关系。

---

## 一、先修口径：`usage_audit.py` 在 DSH 原生日志上返回 0

`usage_audit.py` 读的是 Codex 风格的 rollout 记录：`type=event_msg` +
`payload.type=token_count`，并且要靠 `total_token_usage` 的累计差去重。

DSH 的原生会话日志是另一套 schema：每条 `assistant/message` 自带一个
`data.usage` 块，字段是 `inputTokens / cacheReadTokens / cacheWriteTokens /
outputTokens / totalTokens`，**每次请求一个独立值，不是累计值**。

直接对 `.jsonl.zstd` 解压后的日志跑原有审计，程序不会报错，只会返回：

```json
{"usage_updates": 0, "input_tokens": 0, "cached_input_tokens": 0,
 "output_tokens": 0, "total_tokens": 0, "money_estimated": false}
```

这是一个容易误读的结果——它表示「一条匹配记录都没有」，不表示「没有花 token」。
因此本次新增 `usage_audit_dsh.py`：字段名与 `usage_audit.py` 保持一致，同样要求
显式时区窗口、同样拒绝不一致的计数，只是改为读 v4 的 `data.usage`；不输出任何对话正文。
配套 `test_usage_audit_dsh.py` 覆盖窗口、时区、累计串、拒绝估算四条边界。

## 二、实测总量（单会话 `session-ab501411`，2026-11-01 → 2026-11-10）

| 指标 | 值 | 说明 |
|---|---:|---|
| 用量更新（模型往返次数） | 2,705 | 一次 assistant 消息 = 一次往返 |
| 工具调用 | 2,673 | 与上一条近似 1:1 |
| 对话轮次 | 55 | 含自动续跑 |
| 未缓存输入 token | 2,366,275 | 新计入的提示 |
| 缓存输入 token | 1,103,822,848 | 每步重发的历史上下文 |
| 输出 token | 921,518 | 含推理 token，不另加 |
| 总计（含缓存） | 1,107,110,641 | `input + cached + output` |
| 缓存写 token | 0 | 该供应商不计此项 |
| 压缩（compaction）次数 | 3 次摘要 / 5 次裁剪 | 上下文反复触顶 |

`totalTokens` 恒等于 `inputTokens + cacheReadTokens + outputTokens`，2,705 条记录无一条不满足，
拒绝记录数为 0。

**缓存输入占 99.70%。** 也就是说，这一亿一千万 token 里，真正新读进去的只有 236 万，
真正生成的只有 92 万，其余 99.7% 是把同一段上下文在每一步重新发一遍。

## 三、成本结构：往返次数 × 上下文大小

| 每步提示量（未缓存 + 缓存） | token |
|---|---:|
| 均值 | 408,942 |
| 中位数 | 399,465 |
| 第 10 百分位 | 214,649 |
| 第 90 百分位 | 630,023 |
| 最大值 | 681,001 |
| 会话第一步（最小时） | 7,573 |

2,705 × 408,942 ≈ 1.106e9，与实测总计 1.107e9 吻合。所以成本近似等于：

```
总 token ≈ 模型往返次数 × 常驻上下文大小
```

再看单次观测的体积：1,517 次 `ob` 读页面，返回正文的中位数只有 **227 字节**。
`read_image` 的**文本**载荷中位数 165 字节——但图像本身按图块计费，不在这 165 字节里，
所以这条只能说明「文本观测很小」，不能说明截图便宜。**观测载荷本身不是主因**；
主因是「每读一次，就要把 40 万 token 的上下文再发一次」。

**结论：唯一有量级影响的杠杆是减少模型往返次数。** 压缩观测输出、少写几行日志，
都只能影响常数项。

## 四、往返次数实测：逐步模式 vs 批处理模式

### 4.1 逐步模式（`bc.py ob` / `ct` 逐条驱动）

| 指标 | 值 |
|---|---:|
| 驱动界面的 pwsh 调用 | 1,506 |
| 其中的 `bc.py` 原语 | 2,012 |
| `ob`（读一次页面） | 1,517 |
| `ct`（按文本点一次） | 472 |
| `tap`（按坐标点） | 22 |
| 原语 / 模型往返 | **1.34** |
| 读页面 / 点一次（`ob`:`ct`） | **3.21 : 1** |

`ob:ct = 3.21` 比事前的经验估计（「每个成功动作约 1.8 次多余读取」）更差：
每点一次，平均要读三次页面。

### 4.2 批处理模式（`workflow_session.py`，真机实测一次）

2026-11-06 18:12 的 `run-word3`（`work/ucampus-run/run-word3/checkpoint.json`）：

| 指标 | 值 |
|---|---:|
| 计划步骤 | 1（短词直送 `reflect`） |
| 执行器内部 `bridge_reads` | **70** |
| `clicks` | 0 |
| 执行器 `elapsed_seconds` | 18.063 |
| 模型往返次数 | **1** |
| 模型可见输出 | 898 字节 JSON |

### 4.3 对比结论

把「设备往返」和「模型往返」分开看，才看得清这 70 倍差在哪：

| | 逐步模式 | 批处理模式 |
|---|---:|---:|
| 每次模型往返携带的设备读 | 1.01 | **70.0** |
| 同一批设备动作需要的模型往返 | 每条动作 1 次 | 整阶段 1 次 |

设备动作数量没有减少（反而因为校验更严变多），减少的是**设备动作被暴露给模型的次数**。
这正是「同一工具、不同 agent 策略、成本差一个量级」的机制。

**旁证（非严格同条件）**：会话里有一段窗口可以被外部证据定界——
2026-11-01 20:34–21:56，`work/ucampus-run/` 下依次出现 `listen-20261101-203631.wav`
（Pre）、`while-20261101-204938.wav`、`t2-…211842`、`t3-…212758`、`t4-…213719`、
`t5-…215634`（5 段 While），即 5 个听力任务；同一窗口内没有 `bc.py` 原语，
整段由仓库脚本成批执行：

| 指标 | 值 | 均摊到每个任务 |
|---|---:|---:|
| 模型往返 | 315 | **63** |
| 未缓存输入 | 236,879 | 47,376 |
| 缓存输入 | 73,880,192 | 14,776,038 |
| 输出 | 114,144 | 22,829 |
| 总计 | 74,231,215 | **14,846,243** |

对照：同一会话内改用 `bc.py` 逐条驱动的执行日（11-08）单日 787 次往返、
362,407,771 token。但那天听力与口语的边界无法从日志里无歧义切开，
**因此不对「单个口语任务」给数字**，只把它当作「逐步模式的往返密度确实高一个量级」的旁证。
两个窗口面向不同账号、不同题型，所以这一节给出的是**机制解释**，
不是严格意义上的「同一任务跑两遍」的降幅。

## 五、成因排序（按实测影响，附证据）

1. **没有走整阶段执行器**——主因。1,506 次 pwsh 往返只为携带 2,012 个原语；
   同样的设备工作由执行器做完只需要一次往返（§4.2）。
2. **常驻上下文**——结构性放大。缓存输入占 99.70%，成本随往返次数近似线性上涨（§三）。
3. **试错回读**——`ob:ct = 3.21:1`，每点一次读三次页面（§4.1）。
4. **截图**——238 次 `read_image`。图像 token 无法从日志按调用拆分，
   它混在每步 40 万 token 的提示里；可以说它抬高了常驻上下文，但**不能**给出独立的百分比。
5. **观测输出不紧凑**——影响最小。`ob` 返回正文中位数 227 字节，压到 0 也省不了多少。

事前的两种猜测里，「模型选得不好」不成立：日志里能看到的差异全部落在**往返密度**上，
与具体模型无关；而「没有走整阶段执行器」成立，并且是唯一有量级影响的一项。

## 六、不能从本文得出的结论

- 不是计费金额。`money_estimated: false`；缓存输入与未缓存输入单价不同，本文不做换算。
- 「8.3 MB 压缩日志」是上下文体量的代理指标，**不是** token 数，
  也不能按字节比例推出打包后的降幅。
- 不同题型、不同模型、不同历史长度的会话之间不可直接相乘或相除。
- 本文没有给出「整周总 token 降幅」。要给这个数，必须在同一账号、同一题型、
  同一模型下各跑一遍逐步与批处理两条路线——见下一节。

## 八、复现命令

DSH 日志是 zstd 压缩的 JSONL。Python 3.14+ 自带 `compression.zstd`（PEP 784）；
更低版本用 `pip install zstandard` 后改为 `zstandard.ZstdDecompressor()`。

```python
from compression import zstd
open('session.jsonl','wb').write(zstd.decompress(open('session.v4.jsonl.zstd','rb').read()))
```

```powershell
# 原始审计器：在这套 schema 上返回 0，用于复核第一节的结论
python usage_audit.py session.jsonl --start 2026-11-01T00:00:00+08:00 --end 2026-11-12T00:00:00+08:00

# DSH v4 审计器：产出第二节的数字
python usage_audit_dsh.py session.jsonl --start 2026-11-01T00:00:00+08:00 --end 2026-11-12T00:00:00+08:00

# 只看某个时间窗（第 4.3 节那个听力窗口就是这么做出来的）
python usage_audit_dsh.py session.jsonl --start 2026-11-01T20:34:00+08:00 --end 2026-11-01T21:56:00+08:00

# 按轮次拆分
python usage_audit_dsh.py session.jsonl --start 2026-11-01T00:00:00+08:00 --end 2026-11-12T00:00:00+08:00 --by-turn
```
