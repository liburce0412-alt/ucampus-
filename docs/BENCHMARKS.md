## 新执行器如何验收

本次实现将一组已审阅机械步骤放入一个 Python 进程，复用控制连接，完成后只返回摘要；错误细节和步骤计时留在本地。离线多步测试证明了连续执行与异常停止，但没有因此宣称整周 token 已下降。

下一次同条件测试分别记录：任务和题型、应用/桥版本、网络、必需媒体时长、端到端耗时、模型用量更新、未缓存输入/缓存输入/输出、截图次数和返工次数。先保持内容及模型一致，再比较新旧路线；调试时间单独列出。

优化优先级仍是减少模型往返和返工，其次补齐长口语、完整 AI 对话、长期音乐/游戏共存。8 ms 读取的进一步微优化和未经动态确认的 HTTP 候选不是当前最大收益来源。

这是实际使用记录的比较，当前耗时约为早期的 2.16 倍；题目、上下文、传输/显示路径和调试负载不同，不能当作同条件性能 A/B 或计费估算。两段记录的模型设置都是 `gpt-6.1-terra / max`。旧窗口以 0/5、2/5 的进度报告为界；新窗口从 USB 基线到平台 2/5 回读，包含副屏恢复与锁屏中断。token 截止新窗口结束后的下一秒；外层工具调用包括 exec/wait 等，不是 ADB 指令数或实际模型请求数。这里只统计执行会话，不包含同时段优化会话。

新窗口两段正文媒体合计约 5 分 56 秒，七次短词直送动作合计约 41 秒；它们不含全部短提示音、题意判断和提交。不能把其余时间直接归为网络慢，也不能把工具调用之外的时间全部算作模型思考：后台播放、排队和用户暂停可能与这些间隔重叠。

已确认的返工点：计划第一次导航在点击已派发后仅 0.228 秒，因过渡中的 `no_active_window` 退出；之后又退回逐题开进程、读全树和单独生成操作。`ui_changed/node_changed` 的派发前拒绝也需要人工恢复。新的 Python 修复保留原超时及页面锚点，等待过渡结束，并只对明确未派发的两类拒绝做有界重选；结果未知的动作不重发。

执行侧正在尝试同进程保留转写模型和控制连接。Pre 每次只显示当前词的三个候选，不能提前读完整组；音频中的唯一候选精确命中才允许机械匹配，释义和正文理解仍需判断。该试验尚未整组验收，修复后的端到端耗时与 token 降幅也尚未建立。下一次比较以真实完成一组的时间、人工接管次数和平台进度为准。
